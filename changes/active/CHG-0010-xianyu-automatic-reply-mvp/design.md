# Design

## Architecture

The automatic reply MVP adds `app/xianyu_system/worker/autoreply/` and CLI commands under `python -m xianyu_system autoreply`.

The worker reuses CHG-0009 Wrapper only:

1. Ensure local configuration is enabled and live writes are explicitly allowed.
2. Ensure Pilot health, account logged-in state, and listener connectivity.
3. Establish a startup watermark so historical messages are not replied.
4. Poll `CHAT_NEW_API` inbound messages through `UpstreamWrapper.list_recent_inbound_events`.
5. Normalize and filter inbound text messages.
6. Match deterministic configured rules in order, then optional fallback.
7. Apply safety gates, cooldown, hourly account/conversation limits, and idempotency.
8. Send through `UpstreamWrapper.send_confirmed_reply` with an internal confirmed request generated by the worker.
9. Record non-sensitive audit and state.

## Local configuration

Committed example: `config/autoreply.example.yaml`.

Real local configuration: `.local/autoreply.yaml`, ignored by Git.

Default behavior is fail-closed: `enabled: false` and writes disabled unless both config and `XIANYU_ALLOW_LIVE_WRITES=true` allow it.

## Process management

The CLI supports:

- `python -m xianyu_system autoreply doctor`
- `python -m xianyu_system autoreply run`
- `python -m xianyu_system autoreply start`
- `python -m xianyu_system autoreply status`
- `python -m xianyu_system autoreply stop`

`start` launches one local background Python process and writes non-sensitive PID/state files under `.local/autoreply/`. Repeated `start` detects the running process and does not create a second instance. `stop` stops only the recorded automatic reply process. If this service started the listener, stop also stops it; if the listener existed before start, it is left running.

## Safety

The worker replies only when all gates pass:

- Local autoreply config is enabled.
- `XIANYU_ALLOW_LIVE_WRITES=true`.
- Mode is `dedicated-test`.
- Account is in allowlist.
- Message direction is inbound.
- Message type is allowed text.
- Message is newer than startup/checkpoint watermark.
- No SUCCESS or UNKNOWN idempotency record exists.
- Upstream health, logged-in account, and listener connection are healthy.
- Other Pilot automation counts are zero.

Unsupported message types, outbound messages, safety text, rate limits, cooldowns, missing rules, auth failures, and unsafe configurations fail closed and record only non-sensitive statuses.

## Result handling

- SUCCESS marks message replied.
- REJECTED records a non-sensitive rejection and does not switch path.
- FAILED records failure and does not retry indefinitely.
- UNKNOWN blocks automatic retry.
- SKIPPED records why no send occurred.

## Logging and audit

Runtime logs and state files do not include full message text, full reply text, full account IDs, Authorization, Cookie, Token, Session, passwords, contact details, or upstream payloads. State records rule id, masked references, message hash, result, operation id, and timestamps.
